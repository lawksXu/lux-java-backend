# Session, Run, Turn, and Item: Pre-Schema Design Audit

Date: 2026-10-09

Revision: 2026-10-12

This document records the agreed design and the invariants required before designing tables. It does not define DDL or claim that the new runtime, protocol, or persistence integration has been implemented.

## Scope and ownership

- Java owns business persistence, immutable Session input Items, Tasks, Assets, execution-fact projections, and frontend events. It does not create or schedule Runs, decide execution boundaries, or approve completion.
- Python is the single execution decision maker for each Session. It creates and ends Runs and Turns, maintains model context, and owns the authoritative execution state in LangGraph checkpoints.
- Kafka transports typed Session inputs, controls, and execution facts. Receipt, application, publication, and Java projection are separate states.
- Existing historical development data does not require preservation. Protocol and storage changes must be coordinated so old commands cannot be interpreted as new input.
- The first implementation retains the existing single Python process with exclusive ownership of its local persistence. Multiple workers, separate database copies, and distributed takeover are outside this baseline.

## Domain structure

- Session is the continuous conversation and owns the Item timeline. Input Item bodies have one Java business-storage representation; there is no separate `session_input` table or second business copy.
- Run groups one continuous agent execution. Its reported business status is exactly `RUNNING`, `COMPLETED`, `FAILED`, or `CANCELLED`. `RUNNING` covers all unfinished execution, including preparation, waiting for stop completion, and blocked recovery; Python's internal phase/control state distinguishes those cases. A running Run can absorb additional user inputs at Turn boundaries.
- Turn is one logical model invocation, its corresponding tool executions, and post-processing. Graph preparation and persistence nodes are not additional Turns. Turn states remain `PREPARED`, `RUNNING`, `INTERRUPTED`, `COMPLETED`, `FAILED`, and `CANCELLED`.
- Item is an independently identified record: user or Agent message, exposed reasoning summary, tool call, tool result, or system Task notification. Run/Turn lifecycle facts and cancel, status, replay, start, and end controls are not Items.
- Item source is `USER`, `AGENT`, or `SYSTEM`. Item has no `role`; Python derives provider-message roles from source/kind and preserves the framework's real message/call bindings in checkpoint state.
- USER/SYSTEM input Items always have null Run and Turn fields, including after incorporation into context. They have no consumption binding in Java. All Agent output Items, including TOOL_RESULT, require their actual producer Run and Turn from creation onward.
- MESSAGE and REASONING_SUMMARY share `OrderedContent` with a `blocks` array of `TextBlock(type=text, text)` or `AssetReferenceBlock(type=asset, asset_id)`. Array position supplies content order; neither block has a block ID or index. Full terminal content can reference either a validated uploaded Asset or a validated generated Asset, subject to ownership checks; streaming PARTIAL content contains temporary TextBlocks only.
- Each Run can contain multiple Agent MESSAGE Items. Python selects `final_item_id` and returns that selection with the complete `COMPLETED` Run snapshot. Java persists the selection and validates matching owner/Session/Run identity and a complete MESSAGE from source AGENT when its Item snapshot is available; it never infers the final answer from the last received Item or largest observed Item index. Once a terminal Run's final selection is determined, a later revision cannot change that selection. Item has no `message_phase`; the Run's selected final Item identifies its final answer. An individual Turn need not contain a final answer. Cancelled or failed Runs may have no final answer.
- Streaming updates target a stable Item identity. Output updates never move an Item to a different Java timeline position. Python's stable execution indexes express execution order independently of when Java observes a fact.
- Partial streaming output is distinct from a finalized Item. Persisted partial text does not prove that model context or Turn completion has been committed.
- Each newly applied consecutive text delta appends exactly one temporary TextBlock at the PARTIAL Item content's tail and commits with the updated Item and a Session SSE record carrying the named ItemTextDelta body. It reaches the frontend without waiting for model response, Turn, or Run completion. Deduplication uses Item identity and `stream_seq`; already applied or duplicate deltas do not append or notify twice, and buffered gaps publish when applicable. Final replacement emits typed ItemContentReplaced with the full snapshot; frontend replaces payload/status/source_revision together and rejects stale replacements or any post-terminal delta during replay. Snapshots contain no delta-coverage field.

## Identifiers and ordering

- `item_id` identifies a record; `event_id` identifies one canonical transport event. Every immutable input has exactly one InputAccepted, so its event_id equals Item.id and Item has no separate input_event_id column. Mutable Agent Items have multiple snapshot/delta events with independent event IDs. Republishing preserves each original identity and content.
- Java assigns Item recording/pagination order and SSE delivery order. Its retained `next_item_seq` and SSE sequence values do not define Agent execution order or prove input incorporation.
- Session presentation follows immutable Java Item registration order. Independent USER/SYSTEM inputs split the visible output of one Run into separate stretches; never regroup that Run across intervening inputs or insert later-registered Agent Items before them. For example, M1, A1(R1), M2, A2(R1) remains in that order even though A1/A2 belong to the same Run. Existing A1 streaming updates stay at A1's position; newly registered output after M2 appends after M2. Run/Turn/Item source indexes retain their separate execution-order meaning.
- Readers obtain projection data and its Session SSE high-water mark from the same consistent database snapshot, then replay strictly after that mark. Independently reading the current SSE head and an older projection could otherwise miss committed changes.
- Allocate each immutable input_sequence_no while holding the Session row lock, using a current/locking read of the highest committed input Item sequence plus one. Commit the input Item, original Outbox envelope, HTTP receipt when applicable, and SSE together; concurrent input writers use this same allocator, not an earlier snapshot or a Session execution-progress counter.
- Remove `session.next_event_seq`. Allocate each SSE position from that Session's retained `session_event` records as `COALESCE(MAX(sequence_no), 0) + 1` while holding the Session row lock, using a current/locking read of the latest committed position rather than an older transaction snapshot. Insert the event in the same Java transaction. Retain replay records so a committed sequence cannot be reused.
- Python creates stable `run_id`, `turn_id`, and Agent output `item_id` values. Session-local `run_index`, Run-local `turn_index`, and Turn-local `item_index` define execution order. The corresponding identities and indexes are committed before the operation starts and are retained across recovery.
- The first durable Python Inbox receipt assigns an ordinal to each distinct Session input or control. That ordinal orders admission and stop/wake/control decisions. Input content enters model context in ascending `input_sequence_no`; the two ordering scopes are distinct. HTTP repair and Kafka redelivery preserve the original event identity and never assign an existing event a new ordinal.
- Frozen input identities, execution phase, retained/incorporated input progress, and processed controls are checkpoint state. Java does not require their projection or use them to schedule execution.
- Python's canonical event log assigns a consecutive Session-scoped `event_seq` across Runs once, in the transaction that saves the event and its Outbox entry. All event sources use this allocator. Checkpoint intents do not reserve transport sequences; repeated materialization by event ID returns the original sequence. This sequence supports log-gap detection and replay, not a global barrier for Java entity display. Canonical events cannot be individually removed while their sequence remains part of the replay contract.
- Both TOOL_CALL and TOOL_RESULT Items store the model-provided `call_id`. Matching uses the same owner, Session, Run, Turn, and exact case-sensitive call ID; `UNIQUE(turn_id, kind, call_id)` permits at most one call Item and one result Item per call ID in that Turn. Both kinds require the call ID; other kinds leave it null. A call ID is distinct from an Item ID and a business Task ID.
- Java may persist a result before its call arrives and validate the pair when the actual call is available. Recheck retained Items on call arrival, restart, and synchronization repair; the unresolved relationship cannot depend on an in-memory marker. Item has no `call_item_id` or result-to-call self-FK. A call ID alone cannot establish a TOOL_CALL identity shell or invent its Item ID, index, or content. Python still forms provider context using real checkpointed call/result bindings.
- For the current one-submit_generation-call/one-Task contract, operation_id equals the original TOOL_CALL Item.id. Python persists that original call identity and execution binding before the request and reuses them after restart or UNKNOWN reconciliation. Remove the separate operation_id field from Item and AgentItemSnapshot; keep the named submission, Task, and execution_receipt operation fields with this same UUID value. This adds no Task-to-Item FK and does not require Java's call projection before Task acceptance. Multiple independent submissions in one tool call are outside this contract. An operation identity is not a Task retry relationship; model call_id and HTTP request_id keep their separate correlation/request semantics.

## Input and context persistence

1. Java commits the immutable input Item, its outbound delivery intent, and its Session SSE record in one local transaction. For HTTP message sending, that same transaction saves the `http_request` receipt with owner/key, canonical request hash, and the original response. The Item is the input body; delivery metadata does not create another business input record.
2. Kafka delivers each input independently of Run lifecycle or Session stop. INPUT envelopes are distinct from CONTROL envelopes and Agent EXECUTION_FACT envelopes.
3. Python persists the receipt and original input before acknowledging the Kafka offset. Invalid or conflicting identities are recorded, not silently accepted.
4. A single Session driver merges inputs into LangGraph state at safe Turn boundaries. Active graph execution and an external Kafka consumer do not independently update the same checkpoint thread.
5. LangGraph uses a Session-scoped `thread_id`. Checkpoint state is the sole execution authority: it retains model messages, pending inputs and their ordinals, contiguous retained/incorporated `input_sequence_no` progress, active identities/indexes/status/phase, stop and wake state, processed control IDs, and pending outbound events.
6. Before the next model invocation, the driver selects a fixed admission cut and computes through_input_sequence_no as the maximum of its already incorporated input progress and every admitted pending input's input_sequence_no in that cut. Repair known gaps through that fixed bound before freezing available contiguous pending inputs in ascending input_sequence_no. The last wake alone cannot lower the bound and omit an earlier admitted higher sequence. Inputs arriving after that boundary remain pending for a later Turn or Run.
7. Preparing the context and removing the corresponding queued entries form one state update. Persistence completes before the model step begins. Graph execution uses synchronous checkpoint durability at these boundaries.

Checkpoint receipt progress means that input is retained in persistent state. Context progress means that input is incorporated into the persisted model context. Neither proves that a model request or tool execution succeeded.

HTTP message-send idempotency uses `http_request` exclusively. Reusing the same owner/key with the same request hash returns the saved original response without another input Item, Outbox intent, or SSE event; conflicting request reuse is rejected. Remove Item `client_request_id` and `request_hash` rather than maintaining a second HTTP receipt on the input Item.

Python decides when to create a Run and which retained inputs its first Turn incorporates. There is no Java-created Run command, required-input boundary, accepted/incorporated input watermark, close decision, or wake state. Already incorporated input is not appended again; pending input survives a Run ending.

To repair missing input, Python first inspects its local Inbox, then pages Java's immutable input Items using `after_input_sequence_no`, a fixed `through_input_sequence_no`, and bounded ascending cursor pagination. Join each input to its retained `outbox_event` by event ID equal to Item.id and return the original typed InputAccepted envelope, including its original schema version and occurrence time. On the Java side, the authority for original input protocol metadata is the retained Outbox.envelope; Item has no `input_event_id`, `input_event_hash`, `input_schema_version`, or `input_occurred_at`. Python's technical Inbox may retain its admitted schema version/envelope. Do not reconstruct the event from Item fields or a latest frontend DTO. Retain each input Outbox envelope for the full lifetime of the Session input history; delivered status does not authorize its cleanup while repair is required. The endpoint is read-only and preserves the original version-specific envelope and transport hash. Inbox deduplication compares the original event fields/content or their computed canonical hash; transport `event_hash` remains retained. HTTP and Kafka enter the same logical deduplication path. Repair does not override an existing first-receipt ordinal or retroactively change a stop's effect; newly admitted input receives its first ordinal. Java pagination order does not establish execution progress. The Session driver scans the durable Inbox before sleeping and after checkpoint transitions so receipt racing natural completion or stop cannot lose a wake.

## Normal completion, steering, and cancellation

- Python creates a new Run when an idle Session receives new user input, a terminal Task notification, or an explicit continue control. An idle stop creates no empty Run or Turn.
- Input received during an active Run becomes steering input for the next Turn of that Run. It does not interrupt the current Turn.
- Python decides normal completion and commits its terminal execution state without a Java proposal/approval handshake. Input first received after that decision starts a new Run; Java acceptance of input that Python has not yet received does not keep the old Run open.
- Session stop carries only Session identity and a stable `event_id`, with no target `run_id` or Java input cut. Python applies it according to its first durable Inbox ordinal, completes the already-started Turn including tools and post-processing, then ends the old Run as `CANCELLED` when that Turn completes without an unhandled failure. A confirmed unhandled Turn failure instead finalizes Turn/Run as FAILED, even with stop pending, only after reconciling any remaining IN_FLIGHT/UNKNOWN operation in the same parallel batch. While such an operation remains unresolved, retain the confirmed fatal outcome in checkpoint state and keep the Run RUNNING/recovery-blocked; reconcile the original operations before terminal FAILED, completing the stop effect, or creating a successor Run. UNKNOWN does not establish a terminal outcome. A handled tool error or background Task failure is not inherently a fatal Turn failure. Python does not start another Turn in the old Run or start a Turn merely to save pending input.
- HTTP acceptance and durable control receipt do not prove execution has stopped. Python's checkpoint and canonical stop-effect facts establish the actual outcome. Java may still project R1 while Python has started R2; Java holds no authoritative active execution slot.
- A stop first delivered late acts on execution current when Python processes it. A duplicate with the same event ID restores the original recorded effect; it cannot stop a later Run again. Checkpoint state records processed control identities and their effects before the Inbox application marker is committed.
- Stop preserves all pending input. Pre-stop pending input alone does not automatically restart execution. New user input, a terminal Task notification, or continue after the stop ordinal creates a new wake request.
- A new wake received while the current Turn is finishing is retained. After the old Run is durably CANCELLED, or FAILED because of its confirmed unhandled Turn failure, Python creates a new Run for a retained post-stop wake and processes all pending input. It never resumes the terminal Run, and UNKNOWN cannot authorize a successor. A later stop suppresses earlier wake requests; only a trigger after that later stop can wake again.
- Run replacement preserves Session context, pending inputs, incorporated-input identities, control decisions, and outbound delivery intents. New Run creation resets execution-specific state only.

## Tasks and asynchronous results

The field definitions and import commit boundaries are specified in the [storage design, sections 4.1 and 4.3](2026-10-09-session-run-turn-item-storage-design.md#4-java-task-and-asset-tables).

- Task requires owner and Session association, not mandatory Run, Turn, Item, or original tool-call references. Generation command and callback contracts follow the same boundary.
- Task storage renames `kind` to `file_type` and `request` to `payload`. `file_type` is the IMAGE/VIDEO generation category, not a MIME type or filename extension; `payload` is the immutable named generation request. The adapter maps these columns to the existing submission/connector fields `kind` and `request`; this storage rename does not rename the current v1 protocol.
- Remove Task `request_hash`. For an existing owner/operation identity, directly compare its immutable Session, file_type, and complete original payload using defined typed/JSON-value equality. Identical values return the original Task; changed values are conflicts. Concurrent first submissions rely on owner/operation uniqueness and compare the winning original Task. HTTP request, execution-receipt, event, and intent hashes retain their separate scopes.
- Native provider IDs, original provider submission receipts, polling, and uncertain provider-outcome reconciliation belong to the model connector. Remove Java Task `provider_task_id`; Java validates owner/Session/Task identity and accepts stable connector observations using `provider_event_seq`, the connector's per-business-Task sequence. Native provider IDs are not required in the new Java business callback contract; the existing v1 contract remains the baseline until a coordinated protocol change.
- The new protocol GenerationEvent contains schema_version, event_id, occurred_at, user_id, session_id, task_id, sequence_no, connector_status: ConnectorExecutionStatus, and outcome: GenerationOutcome | null. ConnectorExecutionStatus is ACCEPTED/RUNNING/SUCCEEDED/FAILED; sequence_no maps to Java provider_event_seq. Nonterminal outcome is null; terminal outcome is the matching GenerationSuccessOutcome or GenerationFailureOutcome. Map ACCEPTED to Java SUBMITTED, meaning durable connector admission rather than old v1 provider acknowledgment; RUNNING to RUNNING, including reconciliation/result preservation; SUCCEEDED with a complete manifest to IMPORTING; FAILED to FAILED with error_stage=GENERATION. Java reaches SUCCEEDED only after its Assets are durable and verified.
- GenerationSuccessOutcome has status=SUCCEEDED and nonempty ordered sources. GenerationFailureOutcome has status=FAILED and required GenerationError(code, stage, message, optional provider_diagnostic); its finer stage is VALIDATION/PROVIDER/RESULT_PRESERVATION. Java stores the original code/message with its GENERATION error stage and retains the finer stage/ProviderErrorDiagnostic in the original Inbox envelope. Query timeout, an inconclusive missing execution, or uncertain provider submission does not fabricate a FAILED outcome. These target mappings require a new protocol generation, not reinterpretation of existing v1.
- Retain Task `result_sources` as the immutable ordered `ResultSourceManifest` import handoff whose ResultSource entries contain url, filename, and media_type, distinct from request payload and final Asset references. The connector supplies a complete durable/recoverable manifest; Java saves it before import and maps array positions to Asset.source_index. Identical manifests are idempotent; changed sources or order are protocol conflicts. Recovery uses this manifest plus verified existing Assets; frontend/model queries expose Asset references rather than source URLs.
- Remove Task `last_seen_at` and `last_reconcile_at`. Bounded read-only connector status/replay repair uses pre-result CREATED/SUBMITTED/RUNNING status and existing updated_at; it excludes IMPORTING and does not recover result downloads. Worker timing/throttling is not Task business state. Duplicate observations are deduplicated without generating another Task or provider request, and observations with no business change need not update updated_at.
- Submission immediately returns the named immutable `TaskSubmissionReceipt(type=task_submission_receipt, task_id, accepted=true)`. Acceptance means the Task and submission intent are durably saved; it does not imply provider acceptance. Task submission receipt and Task query snapshot are distinct named TOOL_RESULT content variants, with their original call-ID pairing. A tool failure uses the named `ToolError` with code/message.
- `SubmitGenerationArguments(kind, request: ConnectorRequest)` uses the selected adapter's declared named request schema; `GetTaskArguments(task_id)` carries only the queried Task identity. Execution injects owner, Session, and the original call's operation identity rather than accepting those values as model arguments.
- The original submission tool has one result. Later Task completion never replaces it or creates a second result for its call ID.
- Task terminal states are immutable. This version provides no Task retry operation and no retry association.
- A confirmed generation or result-import failure becomes `FAILED`. Existing unlimited `IMPORTING` retry behavior is removed. The connector retains original provider receipts; Java retains valid partial Assets. Failure records distinguish generation failure from result-storage failure. Recovery of an interrupted, unconfirmed import may reuse verified Assets; it does not reopen a FAILED Task.
- For a valid callback and source, GET/connection/read failures, including HTTP 5xx and timeouts, and content-validation failures are confirmed IMPORT failures: commit FAILED, its notification and Inbox APPLIED, then acknowledge Kafka. Database failures, process/consumer-ownership interruption, or ambiguous object-publication outcomes leave the record unacknowledged for technical recovery of the same event and Asset identities; reconcile uncertain publication rather than blindly declaring FAILED or overwriting bytes. Malformed ownership, event identity, or conflicting protocol content is retained as rejected diagnostics without changing the original Task. This classification does not introduce business Task retries.
- The Java worker receiving a connector result event completes import and its durable business outcome before confirming Kafka consumption. Use the same generation consumer group and owner/Task partition key, disable auto-commit, and process records serially within each assigned partition. The initial implementation uses bounded synchronous processing; different partitions may progress concurrently. Starting a background download and returning success is not completed processing. Workers that may receive redelivery share the Java database and Asset byte store.
- Save and validate the original event identity/content in Inbox without acknowledging Kafka. Keep the result event RECEIVED until its import outcome is committed; identical RECEIVED events resume work, while compatible APPLIED events or intentionally persisted REJECTED diagnostics can complete consumption without repeating business effects. Recover interrupted import through Kafka's uncommitted records and redelivery, with no fixed importer, Task/Inbox import scanner, persisted Task lease, MySQL named lock, or dedicated database connection held across downloads.
- Validate Task ownership, event identity, connector progress, and the immutable accepted manifest. Save the manifest and IMPORTING state in a short transaction while Inbox remains RECEIVED. Reprocessing the accepted event must resume unfinished import even when its connector sequence is already recorded. Compatible duplicates of a terminal Task complete Inbox processing without downloading, reopening the Task, or notifying again.
- Download outside database transactions and database retry callbacks. Use deterministic Task/source_index Asset identities and per-attempt temporary files/objects. Atomically create an absent final object or verify/reuse an existing one; conflicting bytes never overwrite it. Save newly verified Asset metadata in short transactions, and reuse verified objects/metadata after interruption. Duplicate downloads may occur after a crash or rebalance; SQL uniqueness and stable IDs alone do not protect object bytes from a stale downloader. Task version/status conditions and notification uniqueness prevent competing completions from reopening a terminal Task or notifying twice.
- Confirm consumption only after the outcome/APPLIED transaction commits, and acknowledge only the completed prefix of each partition, never beyond unfinished work or to the latest fetched position. A database commit followed by offset-commit failure is recovered by redelivery of the same recorded outcome. Technical failures and incomplete checks must propagate to controlled Kafka redelivery without acknowledgment; recording Inbox retry metadata and returning normally is insufficient. Confirmed business FAILED is acknowledged after persistence and never becomes a Task retry.
- Generic Java Inbox drain excludes generation callbacks, so it cannot launch another import outside Kafka consumption. Existing Java Agent-fact and Python input/control Inbox recovery remain unchanged. Bound total polled-batch work, including downloads, validation, and database work, below max.poll.interval.ms with a margin and a bounded batch size. On revocation or technical interruption, stop further work without treating loss of consumer ownership as Task FAILED. Retain Kafka records for the intended recovery window; unavailable required records need explicit original-outcome replay/repair, not silent offset skipping.
- Uncertain external submission is reconciled using the original operation identity and receipt. It is not treated as permission to regenerate. Delivery retries and read-only reconciliation do not create another Task.
- `SUCCEEDED` requires all declared result Assets to have durable, validated bytes and metadata.
- The first terminal transition commits Task SUCCEEDED or confirmed FAILED, one SYSTEM `task_event` input Item containing only `task_id`, frontend notification/SSE, and outbound delivery intent in one Java transaction under the Session row lock. Result-import completion marks the result Inbox APPLIED in that same transaction before Kafka acknowledgment. Confirmed import failure records IMPORT detail and retains valid partial Assets; temporary database/ownership failures leave the record unacknowledged for Kafka recovery. The Item remains Session-only with null Run/Turn fields and no consumption association.
- Terminal-notification uniqueness is based on the Task identity, not Task version. Progress does not repeatedly wake the model.
- Terminal notification during an active Run is queued for the next Turn. If its Inbox ordinal follows an applied Session stop, it records a new wake even while the current Turn finishes; after the old Run is CANCELLED, or FAILED for a confirmed unhandled Turn failure, Python starts a new Run. Notification after normal completion or stopped execution automatically wakes an idle Session. Earlier pending notification alone does not bypass a later stop; UNKNOWN execution still blocks unsafe succession.
- The UI appends a notification/result card at the Session tail and queries Task/Assets independently. This frontend query is not an agent tool call.
- Python derives the fixed developer notification from source SYSTEM and kind TASK_EVENT. The payload contains only `task_id`; Task details are obtained by a real `get_task` call with a new call ID.
- Each `get_task` result is an immutable, consistent `TaskQuerySnapshot(type=task_query_snapshot, task_id, version, status, assets: list[TaskAssetReference], failure: TaskFailure | null)`. Later updates do not rewrite earlier tool results.

## Checkpoint and delivery consistency

The selected baseline uses recoverable, idempotent commits rather than claiming one transaction across the native checkpointer and separate Inbox/Outbox tables.

- Input/control application saves checkpoint state, ordinal progress, processed identities, and any stop/wake effect first, then marks Inbox application. If the second commit fails, recovery checks the checkpoint and repairs the Inbox marker without appending input, repeating a control effect, creating another Run, or executing the model again.
- Execution state and outbound state-transition intent are saved together in checkpoint state. An intent contains a stable event ID, execution identities, and complete event content. Its transport sequence is assigned when it enters the canonical event log.
- The relay materializes intents into the canonical Session event log and Outbox, verifies identity/content consistency, and commits before the Session driver removes those specific intents from checkpoint state. Their log order does not require Java to wait for earlier facts before persisting/displaying a complete entity snapshot.
- Every later checkpoint inherits intents not yet transferred to Outbox. Run completion, cancellation, and Run replacement cannot discard them.
- Outbox retains responsibility until Kafka acknowledgment. Uncertain acknowledgments may result in repeated delivery with the original identity; the recipient deduplicates it.
- Recovery follows the production Session's current checkpoint lineage. Automatic recovery does not select an older branch and thereby discard newer inputs or event intents.
- Strict local atomicity is possible only with explicit saver/transaction integration covering checkpoint data and related Inbox/Outbox changes in the same actual transaction. Merely sharing a database is insufficient. Such a transaction still excludes Kafka, Java's database, model calls, and external tool side effects.

Reference: [LangGraph checkpoint durability](https://docs.langchain.com/oss/python/langgraph/checkpointers#durability-modes), [native SQLite saver](https://github.com/langchain-ai/langgraph/blob/main/libs/checkpoint-sqlite/langgraph/checkpoint/sqlite/aio.py).

## Streaming output

- Java immediately stores valid execution facts even if a parent fact or earlier event has not arrived. Actual owner/Session IDs, execution IDs, and stable indexes can establish missing entity shells and ownership FKs. Unknown state is left explicitly unknown; shell creation never invents a start, completion, or execution index. Java removes unique guards that would reject multiple projected nonterminal Runs/Turns and has no scheduling `active_run_id`.
- Python persists each Run/Turn/Agent Item `source_revision` with its complete source state and increments it whenever a Python-owned source field changes. Retransmission and recovery reuse the persisted revision for unchanged state. None of these entities stores `source_hash`. Java compares complete Python-owned source fields at an equal revision; equal fields are idempotent and different fields are a protocol conflict. Local Java registration/order/version/timestamps do not participate in that comparison. Technical `event_hash` and `intent_hash` retain their delivery/materialization responsibilities.
- Once an actual Item's kind is determined, it is immutable at every revision; a higher revision cannot turn a MESSAGE into a TOOL_CALL or another kind. A shell leaves unknown kind unspecified until its first valid source snapshot. Terminal Run final_item_id is likewise immutable once determined, independently of later source revisions or parent/Item arrival order.
- For an equal Item revision, validate the incoming source snapshot first. An incoming PARTIAL snapshot is valid only for source AGENT and kind MESSAGE/REASONING_SUMMARY, with `blocks=[]`, null `completed_at`, and the sole initial `source_revision=1`; nonempty or later PARTIAL source snapshots are invalid. Reconstruct the current row's original AgentItemSnapshot from its stored immutable/source fields, substituting empty OrderedContent.blocks only on the current PARTIAL side. Never normalize away invalid incoming content. Terminal and nonstreaming snapshots compare directly with their stored full source payload. Source payload cannot receive presentation or Task-enrichment writeback. No mandatory journal lookup or wrapped synchronization response is needed; retained single-Item events and ExecutionFact.body.items for ModelResponseCompleted remain recovery/evidence sources, excluding rejected records.
- Full entity snapshots update Java atomically only at a newer `source_revision`; an older arrival cannot overwrite the projection. Run/Turn/Item indexes preserve execution order even when facts arrive out of order. Java recording order, SSE order, and canonical cross-Run `event_seq` remain independent. Item snapshots have no delta-coverage metadata.
- Before model invocation, checkpoint stable candidate identities/bindings for possible streamed output; a candidate is not an observed business Item. Publish an Item-start snapshot only after actually observing that Item. Before its first delta, persist and materialize its sole initial PARTIAL snapshot with an empty OrderedContent.blocks array. A delta received first is archived and waits only for that Item's snapshot; an identity shell alone cannot manufacture content or subtype. Unused candidates never become phantom PARTIAL Items or completion-bundle members. The empty initial snapshot need not create a visible empty message. While PARTIAL, each consecutive fragment appends exactly one TextBlock at the tail: no AssetReferenceBlock, merging, deletion, or midstream full PARTIAL replacement is permitted.
- While an Item is PARTIAL, `payload.blocks.length` equals its contiguous applied `ItemTextDelta.stream_seq`: empty content gives 0, delta 1 gives one TextBlock and prefix 1, and delta 2 gives two TextBlocks and prefix 2. This is not a character/byte count or Session event sequence. Java restart and frontend hydration derive the prefix from those existing blocks, without a new field, stream table, or counter inside payload. The retained canonical journal buffers out-of-order deltas; under the Item mutation/Session SSE transaction, ignore an already applied sequence, append the next sequence, and drain any newly contiguous suffix. A gap holds back only that Item's text.
- At the same source_revision, frontend PARTIAL hydration keeps or accepts only the longest matching block prefix. A stale refresh with 5 blocks cannot overwrite 6 already applied blocks; a longer matching prefix can advance the view, while conflicting prefixes require diagnosis/repair. Repeated empty initial source-sync snapshots cannot reset the accumulated temporary blocks.
- A higher-revision COMPLETED or INTERRUPTED snapshot replaces the whole payload/status/source_revision and can repair an earlier delta gap directly, without declaring coverage or requiring every fragment. After that terminal replacement, all late deltas are ignored for projection and SSE regardless of their stream sequence, while their journal evidence remains retained. A terminal payload's block count is not a stream prefix.
- Retain durable live Item-start and text-delta events. A model node can still be executing when these events are observed, so live fragments cannot depend on a node-completion checkpoint.
- The stream writer commits each live event and its Outbox entry through the same canonical event log before publishing it. It does not independently modify the active LangGraph checkpoint. Item identity and its original execution association are durably recorded before publishing the first fragment.
- Materialize the preparation checkpoint's observed Run/Turn state-transition events before starting the model node; candidate bindings do not publish unobserved Item facts. After every stream callback has completed and its event writes have drained, durably save the full original model response and its response-to-Item bindings in execution_receipt. Checkpoint its model-context incorporation, original complete Item snapshots, and pending facts before materialization. Finalization targets the same actual Item IDs as the fragments, and an unstreamed complete response can establish its actual Items directly. A serialized event emitter preserves this order across streaming and checkpoint-derived events.
- Publish the additional named `ModelResponseCompleted` fact only after that original response is durable. It carries the original `model_execution_id`, real Turn identity, and `items: list[AgentItemSnapshot]` with original Item identities, source revisions, and final payloads, without source hashes or delta coverage. Only model-produced MESSAGE/REASONING_SUMMARY/TOOL_CALL Items belong to it; later TOOL_RESULT and SYSTEM/TASK_EVENT are separate facts. One model response may produce multiple Items. Model response completion is distinct from Turn completion, which also includes tools/post-processing, and from Run completion.
- A response bundle has one canonical event sequence and no top-level item_id/stream_seq. Journals retain the complete ExecutionFact envelope, including ExecutionFact.body.items when its body is ModelResponseCompleted, and event hash; recovery/evidence reads accepted nested members as well as single-Item events and excludes rejected records. Existing synchronization returns bare source snapshots. No new response table or per-member source hash is needed.
- Java validates the entire ModelResponseCompleted bundle before mutating any projection. Validate real ownership/identities, complete source content, source revisions, and the strict equal-revision comparison above; a true identity/content conflict rejects the whole bundle projection with durable diagnostics. Stale members and equal-revision identical members are skipped independently. After validation, replace all applicable Items' temporary content with their original response snapshots and write their SSE changes in one database transaction. Missing real parents are established as shells from complete identity/index references in that transaction; missing global journal events do not block the bundle. Archive the original response fact durably and repair projection by replaying that same bundle, without partial application of a conflicting response or an in-memory pending marker. Duplicate or older facts and all post-terminal deltas cannot alter finalized content.
- Canonical event sequences are allocated only for committed events, preventing a failed checkpoint from leaving a reserved sequence gap. Materializing an already transferred intent cannot duplicate the event or allocate another sequence. Log-gap replay never becomes a global Java projection/display barrier.
- Recovery reads the latest checkpoint, confirmed/failed execution receipts, and retained facts before deciding output is incomplete. A saved original model response can restore its same Item bindings, full snapshots, and ModelResponseCompleted fact without another model request, even if checkpoint completion or publication failed. Recovery can replay saved partial output for the frontend while reconciliation remains unresolved; displayed fragments do not prove Turn completion or authorize re-execution.

## Execution recovery

- A stored checkpoint is not proof that every external action completed. Recovery does not blindly replay an entire Turn or automatically resubmit generation.
- Before a Task-submitting tool call, persist the original call Item identity and its operation binding with the same UUID value. Recovery reads an existing receipt or queries that same operation to determine its outcome and recover the original Task ID; it never creates a replacement call Item merely to retry delivery.
- If the outcome cannot be determined, retain Python's internal unresolved recovery phase and block unsafe continuation; the unfinished Run remains `RUNNING`. Preserve recorded tool-call/result relationships before a later model invocation.
- Before every model request, including a successor Run after a fatal failure, require exactly one matching confirmed result or ToolError for every tool call in an incorporated assistant response, preserving its original call_id and checkpointed call/result binding. Reuse confirmed original outcomes and retained context. A call proven never invoked may receive a durable runtime ToolError(code=TOOL_NOT_EXECUTED) explaining its aborted execution, with that original binding persisted before another model request; it is not a provider failure. IN_FLIGHT/UNKNOWN cannot be replaced by this error and blocks unsafe advancement. Java projection completeness does not substitute for this model-context pairing gate.
- An UNKNOWN model outcome keeps its output Item PARTIAL and its Run `RUNNING` with an internal recovery phase; its Turn may be `INTERRUPTED`. Finalize the Item as INTERRUPTED only after confirming that its original response cannot still complete it; reconciliation must not require reversing an already published terminal Item state.
- An external model/tool receipt with `UNKNOWN` outcome is not permission to make the request again. Recovery reconciles the original identity and response binding, including a Task submission's original operation; a confirmed response or failure remains immutable.
- Late execution events retain their original Run/Turn/Item identities. They are not rebound to the currently active Run. Task callbacks independently update their Session-owned Task.
- One OS process lock covers the local Inbox/Outbox store, checkpointer, and Session drivers. An execution thread ID or Java projected active Run is not a substitute for exclusive local ownership.

## Existing behavior to replace

- Remove queued-message edit and withdrawal APIs and their legacy states; the agreed version accepts appended messages only.
- Remove Java Run creation/dispatch, input claims, consumption bindings, accepted/incorporated input progress, wake/closure coordination, and nonterminal Run/Turn unique guards. Java input Items retain null Run/Turn fields permanently.
- Remove Session execution fields, including `active_run_id`, accepted/incorporated boundaries, pending wake, and close decisions. Retain the Item registration counter; remove `next_event_seq` and allocate SSE positions from retained Session event records under the Session row lock.
- Replace expanded Run business states with `RUNNING`, `COMPLETED`, `FAILED`, and `CANCELLED`; preparation, stop waiting, and recovery blocking are Python internal phases/control. Keep Turn states unchanged. Remove Run/Turn/Item `source_hash` while retaining Python-persisted source revisions and strict equal-revision source-field comparison.
- Retain owner/Session/Run/Turn identity FKs and provenance for all Agent outputs, including tool results; permit actual-ID/index shells and revision-checked projections instead of treating delayed Java state as execution authority.
- Preserve Session Item registration order across independent inputs, including when one Run has outputs on both sides of an input; source indexes do not regroup the Session timeline. Read projection and its SSE high-water mark consistently; input writers allocate input_sequence_no under the Session lock using a current read. Item kind and determined terminal final_item_id cannot change at a later revision.
- Remove the single pre-created assistant message per Run and original-card result replacement.
- Use USER/AGENT/SYSTEM source classification and remove Item role. Derive provider-message roles in Python; use shared OrderedContent for MESSAGE/REASONING_SUMMARY with ordered TextBlock/AssetReferenceBlock arrays and no block IDs/indexes.
- Replace streamed block targeting with exactly one temporary tail TextBlock per consecutive fragment; derive the PARTIAL prefix from block count. Remove Item/snapshot `last_included_delta_sequence_no` without adding a replacement field, table, or payload counter. Publish the durable original model response's ModelResponseCompleted fact, validate its whole bundle, and atomically replace all applicable Items with their original complete payloads plus SSE changes. Preserve identity/revision; a true conflict rejects the whole bundle projection, and terminal Items ignore all late deltas.
- Keep stream candidate bindings durable before invocation, but publish initial Item facts only for actually observed output; unused candidates never create phantom PARTIAL Items. Freeze repair through the maximum incorporated/admitted pending input sequence in the selected cut, not only the last wake.
- Remove Item `message_phase` and `call_item_id` plus the result-to-call self-FK. Use Python's Run `final_item_id` for final-answer selection and scoped call-ID matching with separate TOOL_CALL/TOOL_RESULT uniqueness; preserve unmatched results until their actual calls arrive.
- Consolidate HTTP message-send receipts in `http_request`; remove Item `client_request_id`, `request_hash`, `input_event_id`, `input_event_hash`, `input_occurred_at`, and `input_schema_version`. Original InputAccepted.event_id equals Item.id; retain original metadata/envelope only in the existing input Outbox for the Session input-history lifetime. Repair pages Item by `input_sequence_no`, `after_input_sequence_no`, and `through_input_sequence_no`, joins its original Outbox event, and returns that preserved envelope without reconstruction from Item or a latest DTO.
- Remove Item/AgentItemSnapshot operation_id; derive submit_generation's operation identity from its original TOOL_CALL Item.id. Keep Task/submission/receipt operation fields, owner/request conflict checks, and independent output event IDs. No Task-to-Item FK is introduced.
- Remove mandatory Task Run/call references from schema, service validation, immutable submission comparison, and generation envelopes. Rename only Task storage `kind`/`request` to `file_type`/`payload`, with explicit mapping to unchanged submission/connector protocol names.
- Remove Task `request_hash`, `provider_task_id`, `last_seen_at`, `last_reconcile_at`, `import_lease_until`, and retry-oriented import scheduling fields; retain owner/operation uniqueness with direct immutable request comparison, existing technical hashes, connector-owned original provider receipts, and the accepted ordered result_sources manifest for import recovery. Read-only connector query/replay repair uses pre-result status and existing updated_at, excluding IMPORTING/download recovery.
- Replace periodic Task-lease import claiming and callback Inbox polling with Kafka-delivered bounded synchronous result import, serialized within each partition. Remove the proposed MySQL named lock and connection reserved across downloads. Keep result Inbox RECEIVED through completion, preserve short admission/metadata/terminal transactions and immutable object publication, and resume accepted manifest/sequence on redelivery. Commit terminal notification and result Inbox APPLIED before confirming only the completed partition prefix. Technical failures propagate rather than merely recording retry metadata and returning normally; confirmed FAILED is persisted and acknowledged. Other Java Agent-fact and Python input/control Inbox recovery remain unchanged.
- Replace full-snapshot `TASK_UPDATED` tool-message mutation with terminal-only task-ID notification input.
- Define the new GenerationEvent connector_status/outcome contract and map connector ACCEPTED to Java SUBMITTED as durable admission, success to IMPORTING until verified Assets, and typed connector failures to GENERATION failures. Classify confirmed source GET/read/validation failures as IMPORT FAILED with acknowledgment after persistence; infrastructure/ownership interruption or uncertain object publication recovers the original identities without acknowledgment.
- Replace immediate coroutine cancellation and Run-targeted cancellation with Session-only stop at the current Turn boundary. Duplicate control IDs cannot apply a second effect.
- A pending stop cannot mask confirmed unhandled Turn failure: report FAILED, then honor a retained post-stop wake with a new Run. UNKNOWN remains blocked, while handled tool errors and background Task failures do not inherently fail the Turn.
- Remove permanent Java Session queue pause. Python retains old pending input without self-restarting, and later input/Task notification/continue wakes a new Run after stopped execution.
- Keep INPUT, CONTROL, and EXECUTION_FACT contracts distinct. Cancellation, query/replay, and Run/Turn start/end facts do not become model-context or display Items.
- Remove unlimited result-import retries and preserve immutable terminal states.
- Coordinate Java and Python protocol versions and recovery behavior; old payloads cannot be mixed with the new design.
